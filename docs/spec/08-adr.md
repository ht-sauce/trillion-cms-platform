## ADR-001 Monorepo + pnpm workspace

- **日期**：2026-10-05 · **状态**：accepted
- **上下文**：三个应用（admin / geo / server）需要共享内容模型类型；pb-wise 的仓库拆分会导致契约漂移与多发版成本。
- **决策**：单仓库 pnpm workspace（`apps/*` + `packages/*`），根 `package.json` 只放聚合脚本；类型契约放 `packages/shared`。
- **后果**：
  - ✅ 类型一处修改三端同步，杜绝前后端字段漂移；一次安装一次构建
  - ⚠️ 依赖体积集中在仓库根；pnpm 12 的构建脚本拦截策略需要额外配置（`.npmrc`）
- **否决**：npm workspace / yarn workspace

## ADR-002 Nuxt 4 + Element Plus

- **日期**：2026-10-05 · **状态**：accepted
- **上下文**：管理后台需要成熟组件库 + SSR；用户最初提到 Element UI，但它不支持 Vue 3。
- **决策**：管理后台与 GEO 项目统一 **Nuxt 4**；管理后台组件库用 **Element Plus**，配深空控制台暗色主题（CSS 变量覆盖）。
- **后果**：
  - ✅ 两个前端共用同一 Nuxt 版本与相同的构建约定，维护成本更低
  - ⚠️ Nuxt 4 的 import-protection（impound）对导入路径敏感，催生了 `~/config` 别名约定（见 [`03`](./03-frontend-architecture.md) §2.2）
- **否决**：Element UI、Nuxt 3/2

## ADR-003 双模式渲染引擎（SSG / SSR 站点级开关）

- **日期**：2026-10-05 · **状态**：accepted
- **上下文**：GEO 目标要求内容可被稳定抓取（静态化最优），但部分站点需要实时性（会员、时效内容）。二者必须共存且可切换。
- **决策**：`Site.renderMode = ssg | ssr` 作为**站点级开关**；SSG 走手动发布 + 页面级增量构建产出静态目录，SSR 走 Node 实时渲染（按 Host 反查站点）。两种模式共用同一套「模板 + Block」渲染管线与同一批 `public` 接口。
- **后果**：
  - ✅ 切换零内容迁移；SSG 获得 CDN 加速与 Core Web Vitals 优势（GEO 核心）
  - ⚠️ 需维护发布队列与产物替换逻辑；SSG 站点的内容更新有构建延迟
- **否决**：站点永久纯静态 SSG（明确不允许锁死）

## ADR-004 页面 = 模板 + 结构化 Block

- **日期**：2026-10-05 · **状态**：accepted
- **上下文**：GEO 依赖可提取的结构化事实（FAQ、作者、实体、摘要）。富文本自由编辑会让这一切变成不可解析的 HTML 泥团。
- **决策**：页面 = `Template`（槽位序列）+ 结构化 `Block[]`；Block 编辑用「每种类型一个表单」，当前支持 hero / text / faq / imageList / contact；三级模板体系 L1 渲染引擎 → L2 Block 组件库 → L3 站点模板包。
- **后果**：
  - ✅ FAQPage 结构化数据、llms.txt 摘要可全自动生成；发布前体检可自动化
  - ⚠️ 自由度低于富文本；新 Block 类型需要开发而非配置
- **否决**：富文本自由编辑 Block

## ADR-005 站点数据隔离双保险（菜单 + Guard + 查询过滤）

- **日期**：2026-10-05 · **状态**：accepted
- **上下文**：多站点共库 + 行级 `siteId` 隔离，任何一处漏过滤都会造成跨站数据泄漏。
- **决策**：三层防护——① 菜单按角色动态生成（UX）；② `AdminAuthGuard` / `PlatformAdminGuard`（身份与平台级权限）；③ Service 入口 `assertSiteAccess` + 查询经 `siteWhere / siteIdWhere` 强制过滤（**真正的安全边界**）。
- **后果**：
  - ✅ 任意一层失效都不至于直接泄漏；站点管理员与平台管理员权限边界清晰
  - ⚠️ 新增业务接口必须显式接入上述工具，代码评审需检查
- **否决**：仅靠前端菜单隐藏控制权限

## ADR-006 站点表即企业表

- **日期**：2026-10-05 · **状态**：accepted
- **上下文**：站点与企业一对一，需要承载营业执照、信用代码、备案号等资质信息用于合规与 E-E-A-T 信任信号。
- **决策**：`Site` 一张表同时承载网站信息、企业主体、SEO/GEO 默认值、平台配置；管理后台站点列表即企业列表。
- **后果**：
  - ✅ 页面仅一处维护；备案号可直接渲染至页脚（SEO 信任信号）
  - ⚠️ 若未来出现"一家企业多个站点"，需要拆分（当前明确一对一，不做提前设计）

## ADR-007 静态文件 URL 与物理存储解耦

- **日期**：2026-10-05 · **状态**：accepted
- **上下文**：P0 用本地 `uploads/`，未来大概率切对象存储；若业务表直接存 URL 会造成全量改写。
- **决策**：业务表只存 `fileId` 引用，`StaticFile` 表同时记录 `storagePath` 与 `publicUrl`；切存储只改 URL 生成规则 + 迁移脚本。
- **后果**：
  - ✅ 业务零改动；URL 规则集中一处
  - ⚠️ 引用完整性靠业务层保障（未建物理外键）

## ADR-008 双 JWT 域 + 静态站会员岛屿

- **日期**：2026-10-05 · **状态**：accepted
- **上下文**：管理员与站点会员是完全不同的身份域，且静态站无法在服务端读取登录态。
- **决策**：JWT-A（管理域，载荷带 role + siteIds）与 JWT-M（会员域，载荷带 memberId + siteId）分离；SSG 站点的会员功能用 `.client.vue` 客户端岛屿调用 `/api/site-auth/**`。
- **后果**：
  - ✅ A 站会员在 B 站天然无效；管理员 token 不会被会员端点接受
  - ⚠️ 会员相关 UI 必须在客户端渲染，不能出现在 SSR/SSG 直出的关键内容里

## ADR-009 时间口径统一（UTC 存储 / 北京时区输出）

- **日期**：2026-10-05 · **状态**：accepted
- **上下文**：Prisma 对 MySQL `DATETIME` 一律按 UTC 读写，直接用 `toISOString()` 输出会比北京时间早 8 小时（实测）。
- **决策**：落库保持 Prisma 的 UTC 语义不变；对外统一走 `common/utils/datetime.ts`，并在 `main.ts` 覆盖 `Date.prototype.toJSON`，使所有接口输出 `2026-10-05 18:35:40` 形式。**明确禁止**在业务代码里使用 `toISOString()` 输出时间。
- **后果**：
  - ✅ 一次整改全端生效，不再逐个字段处理
  - ⚠️ 引入了对原型的行为覆盖，新增自定义序列化逻辑时需留意

## ADR-010 shared 作为编译型类型包

- **日期**：2026-10-05 · **状态**：accepted
- **上下文**：服务端若直接把 `packages/shared/src` 纳入编译，产物目录会被污染成 `dist/apps/...`。
- **决策**：shared 改为编译型包（`tsc` 产出 `dist/` 的 `.js` + `.d.ts`），服务端 `tsconfig.paths` 指向 `dist/index.d.ts` 且只做 `import type`；`build:server` 内置 `build:shared`。
- **后果**：
  - ✅ 服务端产物结构干净；类型契约仍是单一来源
  - ⚠️ 修改 shared 后必须重新构建才能在服务端生效

## ADR-011 发布串行化 + 产物原子替换

- **日期**：2026-10-05 · **状态**：accepted
- **上下文**：并发构建会写坏同一份产物；失败构建不应影响线上。
- **决策**：`PublishService` 按 `siteId` 加锁（`Set<number>`），同站点并发任务保持排队；构建产物先写 `sites/.<slug>.tmp`，成功后 `rename` 替换正式目录（旧目录先改名 `.old`）。
- **后果**：
  - ✅ 失败不影响线上（旧产物完好）；替换窗口极短
  - ⚠️ 同站点构建需排队，超大站点重建耗时明显

## ADR-012 埋点用 sendBeacon + 内存攒批

- **日期**：2026-10-05 · **状态**：accepted
- **上下文**：v1 监控从简，但不能拖慢页面、不能用第三方 CDN 脚本。
- **决策**：GEO 项目内置 analytics 插件，`router.afterEach` 后用 `navigator.sendBeacon` 上报 `{siteId, path, referrer, anonId}`；服务端限流 + 内存队列攒批写 `track_event`。
- **后果**：
  - ✅ 不阻塞页面、关闭页面也能送达；匿名 ID 不含个人信息
  - ⚠️ SSG 站点要求服务端公网可达；进程异常终止可能丢失少量未落库的批次

## ADR-013 robots 默认放行 AI 爬虫

- **日期**：2026-10-05 · **状态**：accepted
- **上下文**：项目核心商业目标是被 AI 引擎引用，而多数站点默认屏蔽 AI 爬虫。
- **决策**：内置 18 条 AI 爬虫 UA 规则（GPTBot、OAI-SearchBot、ChatGPT-User、ClaudeBot、PerplexityBot、Google-Extended、Bytespider 等），默认全放行；站点级可通过 `Site.robotsPolicy` 精细屏蔽或追加。
- **后果**：
  - ✅ 与 GEO 目标一致，抓取数据可观测
  - ⚠️ 需要向客户说明内容会被 AI 学习；个别站点需手工调整策略

## ADR-014 UI 令牌：12px 字号 / 8px 间距 / 密度优先

- **日期**：2026-10-05 · **状态**：accepted
- **上下文**：管理后台使用者是运营/编辑，需要单屏看到更多行、更多面板，而不是大留白的"展示型"后台。
- **决策**：`$font-size-base: 12px`、间距单位 8px（8/16/24/32 组合）、Element Plus compact 变量覆盖、数字用等宽字体；配色走「深空控制台」（`#0B1224` / `#3B82F6` / `#67E8F9`）。
- **后果**：
  - ✅ 信息密度显著提高，符合 operator 型后台定位
  - ⚠️ 需要持续克制"试试加个更大留白"的冲动；新增组件必须遵守令牌

## ADR-015 文档单文件体系（否决每目录 README）

- **日期**：2026-10-05 · **状态**：accepted
- **上下文**：每个目录一份 README 会造成文档碎片化与快速过时；用户明确否决该形态。
- **决策**：目录与文件说明集中到 `docs/PROJECT_STRUCTURE.md` 一个按目录分级的文件；需求集中在 `docs/REQUIREMENTS.md`；架构集中在 `docs/spec/*.md`。
- **后果**：
  - ✅ 单一维护点，AI 阅读成本低
  - ⚠️ 任何文件增删改都要回头同步 `PROJECT_STRUCTURE.md`（已在 `INDEX.md` §4 立为强制契约）
- **否决**：每目录 README.md、changelog.md、husky / lint-staged / commitlint

## ADR-016 全局配置集中（env/ + config/ + 统一启动器）

- **日期**：2026-10-06 · **状态**：accepted
- **上下文**：三个工程各自维护 `.env`（三份 `apps/*/.env.example`），端口散落在服务端配置、docker-compose 与文档中；本地需开三个终端分别启动，且 admin 与 geo 的 dev 都默认占 3000，冲突只能人工排查。
- **决策**：
  - **值**集中到仓库根 `env/.env.<环境>`（`development` / `test` / `production`）；**结构与派生**集中到根 `config/`（端口表、应用清单、API 基址 / CORS 白名单 / 连接串拼装）
  - 应用不再自带 `.env`，且**不再保留端口与数据库的应用内默认值**（缺失即失败，服务端由 `env.validation.ts` 的 zod 拦截）
  - 新增根命令 **`pnpm allDev`**（`scripts/dev.mjs`）：先结束占用端口的旧进程，再并发启动三端并按应用加日志前缀，Ctrl+C 回收全部子进程；单端 `pnpm dev:*` 复用同一启动器
  - 脱离启动器的命令（`db:*`、`build:*`）统一经 `scripts/exec.mjs` 注入同一套变量，杜绝"两份事实来源"
- **后果**：
  - ✅ 端口与数据库只有一处定义；测试环境可换端口 / 换库，与开发环境同机并存
  - ✅ 一条命令拉起全套工程，端口残留由启动器自动清理
  - ✅ 生产密钥不再散落各工程（`env/.env.production` 不入库，仅保留 `env/.env.example` 模板）
  - ⚠️ 应用不能脱离启动器单独运行（直接 `nest start` / `nuxt dev` 会因缺变量报错）；Docker 形态仍由 compose 显式注入（变量名语义一致）
  - ⚠️ Nuxt 端口必须经 `nuxt.config` 的 `devServer.port` 读取注入的 `PORT`：经 pnpm 转发 `--port` 会被 Nuxt 当作 rootDir 解析并生成 `--port/` 目录（实测踩坑，已写入 `07-deployment.md` §2）
- **否决**：每工程各自 `.env` + 分散读取；引入 `concurrently` / `kill-port`（自研启动器零新增依赖）；把配置放进 `packages/shared`（编译型 TS 包无法被启动脚本与 geo 的 `.mjs` 构建脚本直接引用）

## ADR-017 管理后台采用 SPA（客户端渲染）

- **日期**：2026-10-06 · **状态**：accepted
- **上下文**：管理后台登录态存于 localStorage（要求刷新后保持登录、免服务端会话）。服务端与 SSR 都读不到 token，保持 SSR 会带来三类持续成本：
  1. 受保护页面仍会被 SSR 输出（未登录也能拿到静态 HTML），首屏数据依旧要等客户端请求；
  2. 服务端与客户端登录态不一致 → hydration mismatch，需要在路由守卫里跳过 hydration 阶段、再补一个"挂载后补判"插件兜底；
  3. Element Plus 的 popper 类组件（`el-select` / `el-dropdown` / `el-tooltip`）在 SSR 与客户端结构必然不同，每处都要 `<ClientOnly>` 包裹，且 `el-id-*` 随机前缀还需注入固定种子。
- **决策**：管理后台改为**纯客户端渲染**（`apps/admin/nuxt.config.ts` 的 `ssr: false`）；随之删除 SSR 专用适配（首屏补判插件、ClientOnly 包裹、Element Plus id/z-index 注入种子），路由守卫在浏览器直接按 localStorage 判定。
- **后果**：
  - ✅ 登录态只有一个事实来源（localStorage），行为确定，不存在 hydration 问题
  - ✅ 页面代码回到朴素写法（不必给每个 popper 组件包 `<ClientOnly>`），后台可静态托管
  - ✅ 服务端不再为后台页面做无意义的渲染，接口仍是唯一数据来源
  - ⚠️ 首屏白屏时间略增（HTML 骨架由客户端渲染），后台属于内部工具，可接受
  - ⚠️ 前端守卫只影响体验，**真正的权限边界仍是服务端接口的 JWT 守卫**（不得据此放宽接口鉴权）
  - ⚠️ GEO 项目（`apps/geo`）**不受影响**，继续 SSG / SSR 双模式（GEO 的抓取依赖服务端渲染）
- **否决**：保持后台 SSR（需长期承担 hydration 不一致与逐处 `<ClientOnly>`）；token 改存 HttpOnly cookie 以恢复 SSR 鉴权（改动面更大，且与"localStorage 持久化登录"的要求冲突）

## ADR-018 后台菜单数据驱动（三级结构 + 平台级标记）

- **日期**：2026-10-06 · **状态**：accepted
- **上下文**：管理后台侧栏最初硬编码在 `apps/admin/app/config/menu.ts`，每次调整菜单都要改代码 + 重新构建发版；而需求要求菜单可在后台配置维护，并支持多级（最多三级）。
- **决策**：
  1. 新增 `Menu` 表（`parentId` 自关联，服务端强制最多三级）与 `menus` 模块（`/api/menus/tree` 供侧栏、`/api/menus` CRUD 供管理页）；
  2. 侧栏改为**服务端驱动的递归渲染**（`SideMenuNode.vue`），前端不再保存菜单清单，`config/menu.ts` 只保留角色/状态等字典映射；
  3. 菜单管理入口挂在「系统设置」下（`/settings/menus`），写操作限平台管理员；
  4. 平台级菜单用 `platformOnly` 标记，接口按角色过滤后返回，站点管理员完全看不到。
- **后果**：
  - ✅ 菜单调整无需改前端代码或重新构建；三级结构支持"系统设置 → 子功能"这类分组
  - ✅ 菜单树由服务端按角色裁剪，前端不重复实现过滤逻辑；顶栏面包屑复用同一棵树
  - ⚠️ 侧栏依赖 `/menus/tree`（登录后异步加载），`prisma/seed.ts` 必须包含菜单种子，否则侧栏为空
  - ⚠️ 菜单隐藏仍只是 UX，权限边界不变（见 ADR-005）
- **否决**：继续硬编码菜单（每次调整都要发版）；"前端本地配置 + 后端覆盖"的混合模式（两个事实来源，必然漂移）

## ADR-019 RBAC（用户 → 角色 → 菜单绑定）

- **日期**：2026-10-06 · **状态**：accepted
- **上下文**：ADR-018 让菜单数据驱动之后，菜单可见性仍靠 `Menu.platformOnly` 布尔做二分（平台级 / 非平台级），用户侧则靠 `AdminUser.role` 字符串枚举（`super_admin` / `site_admin`）判断身份。这两者都是硬编码：
  1. 新增"运营管理员""只读审计"这类角色必须改代码（枚举、守卫、前端映射）；
  2. 菜单可见性无法按角色精细控制，只能"全给"或"全不给"；
  3. 用户与菜单之间缺少可运营的中间层。
- **决策**：引入完整的三层绑定 **用户 →（`AdminUser.roleId` 绑定）角色 →（`RoleMenu` 授权）菜单**：
  1. 新增 `Role`（`code` 唯一、`platform` 标记平台级、`builtin` 保护内置角色）与 `RoleMenu`（复合主键授权关系），`AdminUser.role` 字符串改为 `roleId` 外键；
  2. 删除 `Menu.platformOnly`——菜单可见性**唯一来源是角色授权**（服务端保存授权时自动补全上级菜单，保证侧栏可建树）；
  3. `PlatformAdminGuard` 判据改为「角色 `platform = true`」；角色信息随 JWT 下发（`roleId/roleCode/roleName/platform`），避免每请求查库；
  4. 管理后台在「系统设置」下提供**用户管理**（分配角色 + 站点授权）与**角色管理**（CRUD + 菜单授权树）；
  5. 安全护栏：内置角色不可删 / 不可停用 / 不可改标识；不可删除自己；系统必须始终保留至少一个可用的平台级用户。
- **后果**：
  - ✅ 新增角色、调整菜单可见性都变成后台配置，无需改代码或发版
  - ✅ 权限语义收敛到一处（角色的 `platform`），前端不再维护角色枚举映射
  - ⚠️ **角色变更需用户重新登录生效**（角色信息在 JWT 内，最长 `JWT_EXPIRES_IN` 才自然过期）——这是"每请求不查库"的代价，内部后台可接受
  - ⚠️ 种子必须保证内置角色与 `admin` 用户的绑定存在，否则新库无人能进入系统设置
  - ⚠️ 授权是"菜单可见性"层，**不等于接口权限**：接口鉴权仍需各控制器显式挂 Guard（`PlatformAdminGuard` / `site-scope`）
- **否决**：保留 `role` 字符串枚举（新增角色必须改代码）；菜单表保留 `platformOnly` 与角色授权并存（两个可见性来源必然冲突）；为省事让超管角色绕过授权表直接看全部菜单（会造成"授权界面所见与超管所见不一致"，运维无法用超管账号验证授权结果）

## ADR-021 开发期局域网访问（启动器打印本机 IP 入口 + 三端监听 0.0.0.0）

- **日期**：2026-10-06 · **状态**：accepted
- **上下文**：`pnpm allDev` 的入口清单只输出 `localhost`（`PUBLIC_HOST` 派生的 `config.urls.*`）。用手机或其他电脑查看后台 / 站点调试效果时，只能人工 `ipconfig` 找 IP、再拼端口；且即便拿到 IP，默认 `devServer.host` 只绑定回环地址，连接直接被拒。
- **决策**：
  1. `config/index.mjs` 新增 `detectLanHosts()`：**刻意照搬 Vite `resolveServerUrls` 的探测方式**——遍历 `os.networkInterfaces()`、只筛 IPv4、跳过回环，其余全量返回（`family` 兼容字符串 / 数字两种形式），**不做优先级排序、不区分物理与虚拟网卡**；`describeConfig()` 增加「局域网 IP」行（启动第一屏即可见），`describeEndpoints()` 追加「局域网访问」段落（**每个应用一行、列出全部地址**；探测为空时打印提示行，不静默）；
  2. 三个进程监听 `0.0.0.0`：两个 Nuxt 的 `devServer.host` 固定 `0.0.0.0`（端口仍由 `PORT` 注入），服务端 `app.listen(port, '0.0.0.0')` 显式声明；
  3. CORS 白名单在缺省派生时追加本机局域网 IP 的 admin/geo origin（显式 `CORS_ORIGINS` 完全接管，此时需自行加）；
  4. 前端请求出口（后台 `app/config/api/http.ts`、GEO `app/utils/api-base.ts`）做**浏览器端自适应**：基址指向回环地址且页面主机不是回环地址时，把 host 换成当前页面主机名（显式远端域名基址不动；GEO 的 SSR 侧不转换，渲染进程与服务端同机）。
- **后果**：
  - ✅ 启动日志直接给出可点开的局域网地址，手机 / 同网段电脑免配置即可访问
  - ✅ 仅开发形态：生产（Docker / 直装）监听地址与对外入口仍由容器、nginx 决定，不受影响
  - ⚠️ **`0.0.0.0` 意味着同网段任何设备都能访问开发服务**，仅限内网可信环境使用，不要在公共网络下开着 allDev
  - ⚠️ 自适应是"回环基址才跟随页面主机"的窄条件；若显式把 `API_BASE` 指向远端域名，局域网入口仍按远端基址请求（符合预期）
  - ⚠️ GEO 的站点识别仍按请求 Host 匹配站点域名，`192.x.x.x` 通常不在域名表中（本地看站点请用 `NUXT_PUBLIC_SITE_SLUG`；已在 `07-deployment.md` §2.1 注明）
- **否决**：让 `PUBLIC_HOST` 直接填本机 IP（写死在 env 里，换网络即失效）；引入 `vite-plugin-qrcode` 之类第三方（v1 无此需求，且启动器坚持零依赖）；把 CORS 改为开发期放行任意 origin（削弱现阶段的跨域约束，容易掩盖配置错误）；**自建"哪个地址更像局域网"的判断逻辑**（曾按 `192.168 > 10.x > 172.16~31` 排序并识别 WSL / Docker / Hyper-V 等虚拟网卡名——地址段可能不标准、网卡命名各机器不同，容易挑出访问不到的地址；改为与 Vite 一致的全量列出，多网卡时逐行给全，由使用者挑选）

## ADR-022 站点多域名映射（主域名唯一 + 别名域名表）

- **日期**：2026-10-06 · **状态**：accepted
- **上下文**：站点已支持多站点，但每个站点只有一个访问地址 `Site.domain`。实际运营中同一站点常需要多个域名指向同一套内容：`www.` 前缀、不同后缀（`.com` / `.cn`）、历史域名、备案备用域名、临时验证域名。GEO 项目 SSR 按请求 Host 反查站点（`useSiteKey` → `/public/site/:key`），只匹配单个 `domain` 会让别名域名落到"站点不存在"或错误站点。
- **决策**：
  1. **`Site.domain` 仍是唯一主域名**（必填）：SEO 绝对 URL、sitemap.xml、llms.txt、后台列表「预览」继续全部用它，多域名不改变站点的"规范地址"；
  2. 新增 `SiteDomain` 表（`siteId` + `domain @unique`，真实外键 `ON DELETE CASCADE`）承载**别名域名**；**主域名不冗余写入别名表**，避免同一事实两处存储；
  3. 接口层用 `domains: string[]` 表达别名域名，**全量替换**语义（`POST /sites` / `PATCH /sites/:id` 入参、`GET` 出参）；服务端在同一事务内 diff 增删，并校验"别名域名不得与任何站点的主域名或别名域名重复"（冲突返回 `400`）；
  4. `/public/**` 的 `:key` 解析扩展为 `slug | 主域名 | 别名域名`；GEO 侧（`useSiteKey`）**零改动**——它只上报 Host，映射由服务端负责。
- **后果**：
  - ✅ 一个站点可绑任意多个域名，SSR 按 Host 反查一次命中；主域名语义不被稀释，SSG 产物、SEO 元数据链路零改动
  - ✅ 无冗余字段，不存在"主域名两处不一致"；删除站点时别名域名级联清理，不会残留占用域名
  - ⚠️ 别名域名只承载"访问入口"语义，**不做按域名的差异化渲染**（v1 无此需求）；若将来要按域名分流内容，需新增域名级配置字段并重新评估
  - ⚠️ 域名全局唯一由 `SiteDomain.domain` 唯一约束 + 服务端校验共同保证；**`Site.domain` 未加数据库唯一约束**（历史数据可能重复），主域名冲突仅靠服务端校验拦截
- **否决**：把主域名也放进 `SiteDomain` 并用 `isPrimary` 标记（两处真相，所有读 `Site.domain` 的既有代码都要改，收益不足）；用 `Site.domains` JSON 数组（无法建唯一约束与索引，反查需全表扫描）；为别名域名单独开一套 CRUD 子资源接口与弹窗（v1 单站点域名数量少，随站点全量提交更简单，也少一套页面状态）

## ADR-023 站点内容编辑器形态（左树 + 上预览下操作，不做可视化内容编辑）

- **日期**：2026-10-06 · **状态**：accepted
- **上下文**：站点内容需要可视化拼装与快速验证。候选形态有三种：① 每种块写死表单；② 结构化 Schema 注册表驱动表单；③ 可视化拖拽所见即所得编辑内容。
- **决策**：采用「左侧内容树（目录 → 页面 → 块）+ 右侧上部画布预览、下部块列表与数据表单」。画布是承载站点真实外观的 iframe，点树上的块在画布中滚动定位并高亮；**不提供可视化富文本编辑**（守「禁止富文本自由编辑 Block」）。
- **后果**：✅ 编辑者所见即站点真实效果，站点外观与后台主题彻底解耦；✅ 块数据仍是结构化字段，GEO 结构化数据可自动生成；⚠️ 预览必须依赖渲染引擎常驻运行态（见 ADR-024）。
- **否决**：可视化拖拽编辑内容（H 层级与语义化失控、结构化数据失效）；每块写死表单（块增多后后台页面爆炸，且与块渲染/GEO 三处重复维护）。

## ADR-024 块代码化（数据库存 Vue SFC，字段声明与代码同文件）

- **日期**：2026-10-06 · **状态**：accepted
- **上下文**：块既要有开发者级别的自由度（自带结构、样式、交互），又要让后台能生成结构化数据表单与产物；同时块代码要可版本化、可回退。
- **决策**：
  1. 块 = `BlockDefinition` 中的 **Vue SFC 源码**（template / script / scss），后台在线纯代码编辑（CodeMirror + Prettier）；
  2. **字段声明写在块代码内** `defineBlock({ key, name, fields, dataSource })`，服务端用 `@vue/compiler-sfc` 编译校验（失败返回行号并**从源码抽取声明**），后台据此自动渲染块数据表单；
  3. 块代码落盘为 `apps/geo/.blocks/Blk<PascalKey>.vue`（gitignore + 构建前清理），`BlockRenderer` 动态解析渲染，跳过停用块、输出 `data-block-id`、块缺失渲染占位；
  4. 预览走渲染引擎 **dev 模式 + HMR**，保存即热更新。
- **后果**：✅ 新增块类型只需写一个 SFC 文件，后台与渲染引擎零改动；✅ 字段声明与实现同源，不会漂移；⚠️ 块代码在构建与渲染进程执行（等价任意代码执行）——保存页必须常驻风险提示，`key` 白名单、体积上限、仅写白名单文件名；⚠️ 生产环境需要一个 dev 模式的预览进程。
- **否决**：把块代码写在仓库文件里由后台改盘（容器需持久化卷、多副本不一致）；字段 schema 与代码分开由后台可视化维护（与"块编辑=纯代码"路线冲突，多一套编辑 UI）。

## ADR-025 访问地址不可变（页面发布后锁定 slug 与所属目录）

- **日期**：2026-10-06 · **状态**：accepted
- **上下文**：页面 = 模板 + 结构化块，地址由 `path` 物化。若允许发布后改 slug 或移动目录，线上 URL 会变化，需要 301 重定向与历史收录处理。
- **决策**：`status = published` 的页面，服务端**拒绝**修改 `slug` 与 `channelId`（`400 已发布页面的访问地址不可修改`）；目录下存在已发布页面时目录 `slug` 同样锁定；删除已发布页 = 下线清理（清理产物 + 重生成索引），**不写重定向**。改名/移动只允许在草稿阶段。
- **后果**：✅ URL 稳定，无需 301 表与重定向链路，产物路径始终与页面一致；✅ 避免"发布后地址被替换"导致的外部链接失效；⚠️ 运营若确需换地址，只能新建页面并下线旧页（可接受，写入 backlog）。
- **否决**：`PageRedirect` 301 表（当前场景无需求，徒增一套表与运行时拦截）；发布后允许改地址仅做告警（线上链接会断，风险不可控）。

## ADR-026 页面级发布 + 只保留上一版回退

- **日期**：2026-10-06 · **状态**：accepted（**调整** REQUIREMENTS §14 第 10 条"v1 不做版本回退"）
- **上下文**：需求从"块级发布"收敛为"按页面维度更新"；同时要求"支持生产数据回退和修复"。SSG 产物的最小更新单位是 HTML 文件（即页面），不存在"半页产物"。
- **决策**：
  1. 发布粒度 = **单页 / 整站**两种，不做块级；顶部「待发布清单」列出所有有改动页面（含块代码变更牵连的页面）；
  2. 发布前必须二次确认并告知影响线上（受影响页面、线上地址、当前线上版本时间、检查结果）；
  3. 回退 = **只保留上一版**：构建时保留 `.old`（不再删除），提供「回退上一版」；回退只回退产物，不回退数据库内容（回退后该页显示「待发布」），并同步更新该页产物指纹以保证数据与产物口径一致；
  4. 修复 = 整站重建 / 仅重生成 GEO 产物（robots、sitemap、llms、清单）。
- **后果**：✅ 与 SSG 产物粒度天然对齐，实现简单；✅ "保存不影响线上、发布才影响线上"语义清晰；⚠️ 无 N 版历史（写入 backlog，未来若引入 `PageRevision` 表再扩展）。
- **否决**：块级发布（SSG 无对应产物粒度，只能退化为页面级，徒增交互复杂度）；每次构建前整站快照（含客户端资源，体积大）。

## ADR-027 GEO 归属分层 + 机构实体唯一性 + 双模式内容

- **日期**：2026-10-06 · **状态**：accepted
- **上下文**：GEO 元数据容易被散落到块层，导致同一实体在多处重复定义、口径漂移。
- **决策**：
  1. **分层归属**：块只输出语义化结构与 `data-block-id`；页面负责 JSON-LD（按页面类型）、canonical、标题/描述/关键词；站点负责机构实体声明（`MedicalClinic`）、`llms.txt`、`robots.txt`、`robots meta`（完整摘要 `max-snippet:-1`）；
  2. **机构实体唯一性**：实体档案页输出最完整 `MedicalClinic`（`@id` 为 `https://<domain>/#organization`），其他页面只写 `{ "@type": "Organization", "@id": … }` 引用，全站只定义一次；
  3. **双模式内容**：`GeoDoc { mode: 'auto_append' | 'override', custom }`——`auto_append` = 系统生成 + 用户追加拼接；`override` = 只用用户内容、系统不再注入。提供纯计算的生成预览接口，后台可查看**实际会输出**的内容并手动重新生成；
  4. 变量占位符（`{{site.*}}` / `{{page.*}}` / `{{now:YYYY-MM-DD}}`）解析器放 `packages/shared`，仅构建期/请求期解析。
- **后果**：✅ 实体置信度提升（外部信源可稳定指向同一实体）；✅ 自动生成与人工覆盖可共存、可核对；⚠️ 覆盖内容（head 扩展）必须做白名单净化，禁止内联可执行脚本。
- **否决**：把 JSON-LD 声明放进块（块是多页复用的零件，无法表达页面类型与实体语义）；只做全量覆盖（自动生成能力被浪费）。

## ADR-028 增量构建修复（复制现有产物 + 全量索引 + 保留上一版）

- **日期**：2026-10-06 · **状态**：accepted
- **上下文**：现有 `build-sites.mjs` 的页面级增量为「新建临时目录 → 只渲染选中路由 → 整体改名覆盖站点目录」。经代码核对：增量发布会**丢掉站点其他页面**，并使 `sitemap.xml` / `llms.txt` 缩水为只含变更页。这是"页面级发布可用"的前置阻塞。
- **决策**：
  1. 构建开始时**先把现有产物复制到临时目录**（首次构建为空），再只渲染目标路由；
  2. `sitemap.xml` / `llms.txt` / 全站导览一律用**全量已发布路由**生成；
  3. 合并写产物清单 `_trillion.json`（本次页面条目覆盖，其余保留）；
  4. 按 `removedPaths` 清理下线页；归档旧页到 `.history`；
  5. 原子替换后**保留 `.old`**（用于回退上一版），整站重建时才清理冗余 chunk。
- **后果**：✅ 单页发布不再破坏站点完整性；✅ 产物清单成为"页面 ↔ 产物"唯一事实来源；⚠️ 长期增量会产生冗余 `_nuxt` chunk，由整站重建清理。
- **否决**：每次发布都整站重建（站点大时很慢，且与"单页发布"语义不符）；把产物清单存库（与文件双写必然漂移）。

## ADR-029 导航独立配置（内容树不驱动站点导航）

- **日期**：2026-10-06 · **状态**：accepted
- **上下文**：曾考虑"页面树即导航"（一级目录 = 导航分组、页面 = 链接），可省掉一套配置。但站点页面的内部跳转属于**页面开发逻辑**，由块代码自行实现；内容树与后台菜单只承担**可视化管理**职责。
- **决策**：导航独立成 `Navigation` + `NavigationItem`（头部主导航 + 页脚四列），导航项引用页面或外部链接、可排序；配套导航管理页。内容树**不参与**导航生成。
- **后果**：✅ 站点的信息架构与后台管理结构解耦，客户差异可以很大；✅ 门面（页头页脚）改动不需要动内容树；⚠️ 多一份配置维护成本（页面改名/下线时导航项可能失效，后台对失效项告警）。
- **否决**：树即导航（把后台管理结构强加给站点 IA）；把导航写死在块代码里（纯运营变更也要改代码并重新构建）。

## ADR-030 站点下载（完整包 / 纯静态包）

- **日期**：2026-10-06 · **状态**：accepted
- **上下文**：建好的站点产物需要能拿到别处部署（CDN、客户自有服务器），且使用者可能没有代码能力。
- **决策**：站点列表与编辑器提供「站点下载」，`mode=full`（HTML + `_nuxt` + `_payload.json` + robots/sitemap/llms + 产物清单 + 部署说明）与 `mode=html`（仅 HTML 与 GEO 产物 + 清单）两种；流式打包不落临时大文件；下载前若存在未发布改动需二次确认（下载的是上次构建产物）；动作记审计日志。
- **后果**：✅ 无代码能力者也能拿到可直接托管的产物包；✅ 包内含产物清单，部署方可核对版本；⚠️ `html` 模式不含客户端资源时页面交互与会员岛屿会失效（属声明边界）；⚠️ 一期仅支持根路径部署，子路径（baseURL）写入 backlog。
- **否决**：只提供完整包（CDN 回源场景体积浪费）；在后台做"打包构建"二次产物（重复构建、口径易漂移）。

## ADR-031 站点前缀复用 slug + 本地回环地址按 URL 前缀解析站点

- **日期**：2026-10-07 · **状态**：accepted
- **上下文**：本地开发时多个站点共用同一个 GEO 端口（3002），`Site.domain` 的本地值又都是 `localhost:3002`，后台站点列表「预览」因此总打开同一个站点——SSR 按 Host 只能解析出一个站点，无法区分。需要让预览精确落到目标站点，且不引入数据库迁移。
- **决策**：
  1. **站点前缀复用 `slug`**（站点标识 / SSG 产物目录名），不新增字段：预览地址统一为「主域名 + `/{slug}`」（本地即 `http://localhost:3002/<slug>`），站点编辑页可改；
  2. GEO 侧 `useSiteKey` 升级为「站点上下文解析」，按运行形态分流：SSG 构建期用 `NUXT_PUBLIC_SITE_SLUG`（URL 路径即产物路径，不解析前缀）→ 非回环 Host 用域名（ADR-022）→ **回环地址（`localhost` / `127.0.0.1` / `0.0.0.0` / `[::1]`）用 URL 首段作候选站点前缀**；
  3. 首段必须**经服务端确认确为站点**（探活 `/public/site/:key`，`findSiteByKey` 支持 slug / 主域名 / 别名域名）才认作前缀，否则回退 `NUXT_PUBLIC_SITE_SLUG`——避免站内不带前缀的路径（`/doctors`）被误判成站点标识；
  4. 前缀只是**访问入口**：`usePage` 在请求页面前 `stripSitePrefix`（`/<slug>/visit` → `/visit`），渲染引擎拿到的 path 与线上产物一致；服务端接口、JSON-LD / canonical、SSG 产物路径零改动；
  5. 解析结果存 `useState` 并随 SSR payload 传到客户端，站内导航（无前缀）不再触发二次探活，也避免 hydration 漂移；
  6. **内容编辑器的预览票据地址同样带前缀**：`POST /preview/ticket` 返回的 iframe `url` 统一走 shared 的 `buildSiteUrl`（基址取 `preview.geoBaseUrl`），回环基址自动带 `/{slug}`——否则 iframe 打开的是无前缀路径，会退回默认站点，表现为「预览 B 站点却看到 A 站点」；
  7. **回环地址下前缀恒等于站点标识，站内路径统一补齐**：解析出的 `prefix` 不再只是"第一个请求才有"，默认站点同样带前缀；新增全局中间件 `apps/geo/app/middleware/site-prefix.global.ts`，在**唯一一处**把缺前缀的页面路径改写成 `/<slug><path>`（query 与 hash 原样保留，故预览票据不丢），一次覆盖首屏 SSR、客户端导航（含 Block 里写死的 `to="/visit"`）、刷新与新窗口；
  8. **站点地址只允许一处拼装**：规则收敛到 `@trillion/shared` 的 `utils/geo-url.ts`（`LOOPBACK_HOSTS` / `hostnameOf` / `isLoopbackUrl` / `normalizeBaseUrl` / `siteUrlPrefix` / `buildSiteUrl`），服务端预览票据、管理后台站点列表「预览」、GEO 的回环判定共用同一份，避免三处各拼一套而漂移。
- **后果**：
  - ✅ 本地多站点共用端口也能精确预览目标站点；零数据库迁移、零服务端接口改动（只多一次站点探活，且仅发生在回环地址）
  - ✅ 线上（域名访问）与 SSG 构建行为完全不变，产物仍是 `sites/<slug>/index.html`
  - ✅ 站内跳转、刷新、新窗口、复制地址都不掉前缀：回环地址下 URL 始终是 `http://localhost:3002/<slug>/...`，不再回退默认站点；预览票据随跳转保留，预览态不会被内链打断
  - ⚠️ 回环地址下不带前缀的地址（`http://localhost:3002/`、`/visit`）会 302 到默认站点前缀（`/star-tech`、`/star-tech/visit`）——「无前缀」只能解读为默认站点，无法凭空推断用户想看哪个站点
  - ⚠️ 局域网 IP 主机（`192.x.x.x`）仍走域名匹配、无前缀，预览仍以 `localhost` 前缀地址为准
- **否决**：新增 `urlPrefix` 字段（与 `slug` 语义重复，还要迁移并同步产物目录）；本地无条件把 URL 首段当前缀（不带前缀的内页会被误解析成站点）；无前缀时"记住上次访问的站点"（需跨请求状态，SSR 不成立）；把预览改成独立端口或子域名（要动端口表与启动器，成本更高，且不解决"域名即站点"的本源冲突）；在页头/页脚与每个 Block 内各自拼前缀（用户代码与导航配置都得改，漏一处就掉站，故改由中间件统一补齐）。

## ADR-032 发布性能优化（编译 worker 化 + 构建缓存 + SSR 爬取 + 失败隔离）

- **日期**：2026-10-07 · **状态**：accepted
- **上下文**：发布链路存在双重浪费与阻塞风险——① 保存块时已完整执行 Vue SFC 编译（校验用），产物随即丢弃，发布时 `nuxt generate` 又把全部块连同整站资源从零重编；② SFC 编译与 Vite 构建都是非 IO 密集的 CPU 重活，在 Node.js 单进程里会阻塞 NestJS 主事件循环，一次保存/发布可能让所有在线请求停顿甚至拖垮服务；③ 任何失败都不能影响线上已有产物。
- **决策**：
  1. **块编译 worker 化**：`@vue/compiler-sfc` 的 parse/compileScript/compileTemplate/compileStyle 移入 `worker_threads`（`apps/server/src/common/workers/sfc.worker.ts`，一次性 worker + 15s 超时），超时/崩溃归一为 400 错误，不回退主线程编译；仅 worker 产物缺失（未编译源码环境）降级主线程并告警。保存路径增加 `codeHash` 短路：同一份代码重复保存直接复用上次结果；
  2. **编译产物不落库**：发布端消费的是「构建缓存 + SSR 爬取」链路，不消费块的 JS/CSS 编译产物，落库只是死存储；保存时的编译职责收敛为「校验 + 抽取声明」；
  3. **发布去整站重编译**：`build-sites.mjs` 改为三元组指纹（块 `blockHash` + 应用 `appHash` + `apiBase`）判定构建缓存（`apps/geo/.<slug>.build/`：`meta.json` + 上次 `nuxt build` 归档的渲染服务）。命中 → 跳过 Vite（发布开销的大头）；失效 → 执行一次 `nuxt build` 并归档进站点缓存。**缓存必须放 geo 根且内容直接放根层**：Nitro 构建期把绝对 `publicDir` 相对化到 `.output`（`../sites/<gen>`），渲染服务运行时按同层级基准解析——层级错一位则静态文件全 500、爬取全灭（实现期实测踩坑后固化为位置约束）；
  4. **SSR 爬取替代预渲染**：无论命中与否，随后拉起缓存的渲染服务，按 `Host: <slug>` 逐页请求本次 targets，产出 HTML + payload 到 `.gen`——渲染开销从整站冷构建降为 O(目标页)；再合并进现有产物副本（沿用 ADR-028 的先生成后合并顺序）；
  5. **跨站点构建互斥锁**：`sync-blocks` 写共享 `Blk*.vue`、`nuxt build` 读写根 `.nuxt/` 与 `.output/`，并发构建会缓存投毒。锁文件 `sites/.build.lock`（pid + 起始时间）覆盖 sync → build → 归档段，之后的爬取与合并只碰站点私有目录可并行；等锁 30 分钟超时，陈旧锁（pid 已死或 >45 分钟）直接接管；
  6. **发布任务与进程级失败隔离**：`publish.service` 的任务执行全链路 try/catch + 状态防重入 + 超时强杀（`BUILD_TIMEOUT_MS`，默认 15 分钟，SIGTERM→5s→SIGKILL）+ 启动恢复（悬死任务复位 pending）+ 按站点串行链；`main.ts` 拦截 `unhandledRejection` / `uncaughtException` 只记录不退出；
  7. **失败不落线上**：页面渲染非 200 → 脚本非零退出，合并/替换不发生；产物替换用 rename 原子操作，`.old` 保留上一版。
- **后果**：
  - ✅ 内容编辑发布（不改代码）跳过 Vite，开销从整站冷构建降为 O(目标页) 爬取；同码重复保存零编译
  - ✅ CPU 重活全部离开主事件循环，保存块不再阻塞在线请求；发布任务任何失败都被任务层/进程层兜底隔离，不崩溃服务、不影响线上
  - ✅ 跨站点并发发布由互斥锁串行化共享目录操作，崩溃遗留锁可自动接管
  - ⚠️ 缓存三元组任一变化即全量重建（依赖升级、nuxt.config 改动都会触发），首次发布仍需一次完整 `nuxt build`
  - ⚠️ 爬取期间渲染服务常驻内存（约一个进程），构建锁外并行爬取允许多站点同时各起一个
- **否决**：编译产物（JS/CSS）落库复用（发布链路不消费，死存储且与 Vite 产物格式耦合）；用 `cluster`/多进程包整个服务端（复杂度高，worker 线程已解决单点阻塞）；发布失败时回滚线上产物（原子替换 + 不落线上已覆盖该场景，回滚引入双倍状态管理）；把构建缓存放系统临时目录（跨站点共享判定需要稳定路径，且清理策略与站点绑定更清晰）。

## ADR-033 产物清单写入对齐契约（修复既有缺陷）

- **日期**：2026-10-07 · **状态**：accepted
- **上下文**：`sites/<slug>/_trillion.json` 是「页面 ↔ 产物」对应关系的唯一事实来源（09 §8.2），其字段契约早已由 `packages/shared/src/types/editor.ts` 的 `ArtifactManifest` / `ArtifactPageEntry` 定义，**但构建脚本从未按契约写入**——实际写的是 `{ buildId, builtAt, totalRoutes, pages: 路由对象数组（含 id）, routes: 路由对象数组 }`。后果（均为实测）：
  1. 后台 `ArtifactsService.pageEntry()` 按 `pages[].pageId` 查 → 条目里只有 `id` → 恒落空，页面徽标恒为「产物缺失」；
  2. 后台 `lastBuiltAt()` 读 `generatedAt` → 实际字段叫 `builtAt` → 恒 null，「当前线上版本时间」永远为空；
  3. 清单合并按 `page.id` 归并，而历史遗留条目只有 `pageId` → key 为 `undefined` → 条目只增不减（2 页站点实测累积 3 条）；
  4. 回退流程 `readOldManifestEntry()` 按 `pageId` 取上一版指纹 → 恒落空，回退数据源不可用。
- **决策**：
  1. 构建脚本按契约写清单：`buildId / siteId / slug / domain / generatedAt / routes: string[] / pages: ArtifactPageEntry[]`，`fileHash` = 产物文件 sha1 前 16 位，`blocks[].codeHash` 透传自公开接口；
  2. `GET /public/routes/:key` 的 `blocks[]` 补 `codeHash`（站点私有块优先覆盖同名公共块，口径与 `BlocksService.codeHashMap` 一致）；`PublicService` 直查 prisma 而不注入 `BlocksService`——`BlocksModule` 已依赖 `PublicModule`，反向注入会成环；
  3. 合并只接纳 `pageId` 为数字的旧条目，历史错误格式条目在下次构建自然淘汰；
  4. 契约以 shared 类型为唯一权威，脚本与后台均不得自造字段名。
- **后果**：
  - ✅ 发布徽标、「当前线上版本时间」、回退指纹、产物统计全部恢复可用；清单不再累积脏条目
  - ✅ 增量构建（只重建目标页）与未重建页条目共存时口径一致（按 `pageId` 覆盖）
  - ⚠️ `scripts/` 参与应用指纹（appHash），脚本改动会触发一次 Vite 全量重建（可接受，一次即回到缓存命中）
  - ⚠️ 历史产物清单里的错误条目不会被主动迁移，靠下一次构建自然淘汰
- **否决**：修改 shared 契约去迁就脚本输出（后台三处消费方都得跟着改，且放弃 `pageId` 会让回退与徽标无键可依）；保留旧格式另写一份清单（双份清单必然漂移，违背「唯一事实来源」）；在后台做格式兼容层（把缺陷固化进消费端，后续每处读取都要兼容两套字段）。

## ADR-034 代码上线与数据库上线分离（两条独立命令）

- **日期**：2026-10-07 · **状态**：accepted
- **上下文**：`env/.env.test` 与 `env/.env.production` 早已存在，但只有**开发形态**一条命令（`pnpm allDev`：源码直跑 `nest start --watch` / `nuxt dev`）。要用测试/生产环境真上线，得手工按顺序敲 `build:shared` → `build:server` → `build:admin` → `build:geo`、再想办法跑迁移、再分别启动四个进程：
  1. **顺序无人保证**：先迁移后构建会留下「新结构 + 旧代码」的不一致窗口（旧进程读新表）；先构建后迁移又可能忘了哪一步；
  2. **数据库增量发布缺入口**：唯一的迁移命令是 `pnpm db:migrate`（`prisma migrate dev`），它是开发向命令（交互、会提示 reset 开发库），**不能用于测试/生产**；[`04`](./04-data-model.md) §6 已要求「手工维护 SQL + `migrate deploy` 应用」，却没有对应命令，上线时只能手敲 prisma 子命令；
  3. **没有体检**：用错环境文件、`JWT_SECRET` 还是占位值、生产 `PUBLIC_HOST` 还是 `localhost`，都要靠人记；端口残留也要人工排查（此前只有 `allDev` 做端口清理）。
- **决策**（首版曾把迁移并入代码上线器，**同日修正为分离**——数据库发布需要独立的执行时机与审计点）：
  1. **代码上线独立成命令**：`pnpm release:test` / `release:prod` / `release --env <name>`（`scripts/release.mjs`，零第三方依赖），顺序固定为：**体检 → 构建 → 释放端口 → 生产模式启动 → 就绪探测与健康检查**；任一步非零退出立即中止，不做「尽力而为」；**该命令绝不执行任何迁移**；
  2. **数据库上线独立成命令**：`scripts/db-release.mjs` + `pnpm db:deploy` / `db:deploy:test` / `db:deploy:prod`（`--env` 亦可透传），顺序固定为：**体检（生产库口令为空/占位值 → 阻断，防改错库）→ 只读检查（`prisma migrate status`）→ `prisma migrate deploy` → 复核**；另设 `pnpm db:status[:env]`（`--check`，只读）；`pnpm db:migrate` 明确限定「仅本地开发」；
  3. **两条命令之间的接线**：代码上线器的体检做**只读**迁移检查——目标含服务端时，结构落后（有未应用迁移 / 库不存在 / 不可达）即**阻断**并提示先跑 `pnpm db:deploy --env <环境>`（确需先上代码再 `--force`）；目标只有 `admin` / `geo` 时跳过（前端不依赖数据库连接）；
  4. 生产形态各应用统一走 package.json 的 **`start:prod`**（服务端 `node dist/main`；两个 Nuxt 应用 `node .output/server/index.mjs`，与 `docker/Dockerfile.frontend` 的 CMD 同口径）；脚本名集中声明在 `config/apps.mjs`（`devScript` / `buildScript` / `startScript`），开发启动器与上线器各取所需；
  5. **体检阻断制**：`JWT_SECRET` 占位值或长度不足、`PUBLIC_HOST` 仍是回环地址、生产缺 `CORS_ORIGINS`、生产库口令为空、`--skip-build` 但产物缺失 —— 全部逐条列出，`error` 级阻断（`--force` 才放行）；
  6. **端口清理逻辑抽出** `scripts/port-guard.mjs`（netstat/taskkill、lsof/kill），`dev.mjs` 与 `release.mjs` 共用一套，上线同样「先结束占用端口的旧进程再启动」。
- **后果**：
  - ✅ 上线被拆成两个各自独立、各可重复执行的命令：结构变更 → `db:deploy`，代码发布 → `release`；两者都有 `--check` 只体检可先跑
  - ✅ **代码上线器在任何路径上都不写数据库**，因此任何一步失败都不可能留下「新结构 + 旧代码」或「旧结构 + 新代码」的不一致；数据库侧只做增量应用、绝不 reset，空库首次部署也会建库
  - ✅ 审计清晰：库结构变更永远只发生在 `db:deploy` 这一条命令里（谁在何时改了哪个库，一眼可见）；入口与健康检查结论落盘仓库根 `release-endpoints.txt`（不入库）
  - ⚠️ 完整上线是**两条命令**（结构变更时）：先 `pnpm db:deploy:<环境>` 再 `pnpm release:<环境>`；代码上线器的体检会拦下「忘了先迁移」的情况，但拦不住「本次迁移与新代码无关」这类语义判断——顺序的合理性仍需人来确认
  - ⚠️ `env/.env.production` 不入库，`PUBLIC_HOST` / `CORS_ORIGINS` / 库口令等必须人工确认——体检只能拦「明显没改」的占位值，不能代替上线前的逐项核对
  - ✅ 开发与上线共用同一份 `config/` 派生（端口 / API 基址 / 连接串 / CORS）与同一套端口清理，不存在两份事实来源
  - ⚠️ 上线器在**前台托管**三个进程，Ctrl+C 一并结束；长期常驻仍应交给 systemd / Docker（见 [`07`](./07-deployment.md) §1）
  - ⚠️ `allDev:test` / `allDev:prod` 保留（开发形态跑测试/生产环境文件，用于本地联调）；上线请用 `release:*`，两者区别已写入 07 §1 与 §3.2
- **否决**：把数据库迁移并进代码上线器（结构变更会被藏在「上线」里，执行时机、影响面与审计点都被掩盖——首版如此，同日修正）；引入 `pm2` / `forever` 之类进程管理器接管（新增依赖与运行形态，与「根脚本零第三方依赖」「Docker / systemd 两种既有部署形态」冲突；本命令定位为直装形态的一键操作）；上线/数据库命令自动 `prisma db push` 或自动 reset（`db push` 绕过迁移历史，reset 会毁数据）；体检做成交互式确认（不可自动化、易被回车跳过，改为阻断式 + `--force` 显式放行）。

## ADR-035 块隔离：公共块降级为模板，站点引用即复制副本

- **日期**：2026-10-07 · **状态**：accepted
- **上下文**：原口径下 `BlockDefinition` 的公共块（`siteId = 0`）**直接被所有站点共享渲染**（`codeHashMap` / `rendererManifest` 是「站点私有块优先 + 公共块兜底」）。后果是站点之间没有隔离：A 站在块库改一次 `hero-dark`，B 站同 key 页面下一次发布就会带上 A 站的改动（块代码指纹进页面内容指纹），而 B 站运营对此毫不知情。这与「站点数据必须按站点隔离，不得影响其他站点」的硬要求冲突：
  1. 公共块的定位本来就该是**模板**（提供一份可用的初始实现），而不是跨站共享的运行时依赖；
  2. 站点一旦投入使用，业务方期望「这个块从此归我」——改它不该牵连别人；
  3. 真正的共享需求（一次改、全站群生效）在本期并不存在，也不该用「共享同一行记录」这种最粗暴的方式实现。
- **决策**：
  1. **语义**：`siteId = 0` 的行是**公共模板（模板库）**，只作模板，**不再是任何站点的渲染来源**；站点块（`siteId = 站点 id`）是站点的唯一渲染来源与内容指纹依据；
  2. **复制时机**（`copyTemplatesToSite`，幂等，只有一处实现）：保存草稿（站点首次引用）→ 建站导入 → 发布前兜底（`PublishService.enqueue`，失败仅告警）→ 块库「引入本站」按钮 → 存量数据由 `prisma/backfill.ts` / `prisma/seed.ts` 补齐；
  3. **读取兜底**：`codeHashMap` / `rendererManifest` / `PublicService.routes` 保留「本站块优先 + 公共模板兜底」，仅用于「半迁移数据不出现块缺失」，不是隔离的依赖路径；
  4. **权限**：模板库（`siteId = 0`）任何读写都是平台级（`assertSiteAccess(user, 0)`），站点块的读写为站点级；站点尚未持有某块时读接口回落到模板（先看字段声明），此时保存会先复制再落笔；
  5. **界面**：内容 / 页面 菜单下并列「块库」（本站块 + 可引入的模板）与「块模板」（模板库，平台级）；块代码页以**新标签页**打开，避免离开工作台后现场丢失；
  6. **不改表结构**：`scope` / `siteId` 字段与唯一键沿用（`siteId = 0` 即模板），只改语义与调用链——无需数据库迁移，`prisma/backfill.ts` 负责存量数据补齐。
- **后果**：
  - ✅ 站点之间彻底隔离：A 站改块代码不影响 B 站；改模板只影响「之后新引入」的站点
  - ✅ 运营心智简单：块用过就是「本站的」，模板只是起点；块库能看清「哪些模板还没引入」
  - ✅ 无需迁移脚本改表结构；存量数据一次回填即可对齐
  - ⚠️ 同一份模板会被复制成 N 份（N = 使用该块的站点数）——这是隔离的必然成本，块是源码文本、量级可控；代价是「修所有站点同名块」需要逐站操作（本期无批量下发需求）
  - ⚠️ 模板改动对已引入站点不可见，若期望「模板升级」需人工逐站同步——`backfill` 与「引入本站」都不会覆盖已有副本（幂等跳过），这是刻意的：**绝不静默覆盖站点已改过的代码**
  - ⚠️ 发布兜底会在 `enqueue` 里做一次站点内页面块 key 收集，整站发布时读取站点全部页面（量级在百级，可接受）
- **否决**：让站点直接共享公共块（就是当前要修的缺陷）；引入「块继承 / 覆盖链」跑时合并（复杂度高、排障困难，且同样解决不了「改动只影响本站」的直觉诉求）；把模板与站点副本做成同一行加 `siteId` 数组（MySQL 无法用唯一键保证 `[key, siteId]` 的多值语义）；在模板改动时批量覆盖所有站点副本（会静默毁掉各站已定制的内容）。

## ADR-036 设计稿样式原样落地（不转写为令牌化 SCSS）

- **日期**：2026-10-08 · **状态**：accepted（修正 ADR-024 的落地方式，不改块代码化本身）
- **上下文**：`09 §7.4` 原文只说「设计稿 `assets/theme-b.css` 的令牌转写为站点 `themeTokens`」，没说样式**类体系**怎么处理。首次完整建站按「只转令牌、类名自己写」执行，结果是 41 个块组件用自创类名（`.hero-dark` / `.service-card` / `.device-row`）+ 每块 scoped 样式重写了一遍视觉，**与设计稿逐页比对明显不一致**（间距节奏、卡片结构、栅格断点全都对不上），且设计稿一改就得重新翻译。同时 `09 §7.4` 自身把 `--bg` 记成了 `#F5F8FC`（设计稿实为 `#FFFFFF`），错值被合法化后传进了三处默认值真源。
- **决策**：
  1. **样式层**：设计稿 `theme-b.css` + `site.css` **逐字节复制**到 `apps/geo/public/assets/css/`，由 `app.vue` 引入。原型 CSS 只允许**追加**补充规则，不得改动原选择器与声明。
  2. **组件层**：块组件与框架组件的 HTML **直接复用原型类名与 DOM 结构**，不自创类名。块组件的 `<style>` 仅在原型 CSS 不足时做最小追加，不得覆盖原型布局。
  3. **令牌桥接**：原型 `:root` 令牌与 §7.4 注入的变量**同名**（含 `--r-sm/--r-md/--r-lg` 别名，映射到 `--radius-sm/md/lg`），因此原型 CSS **零改动**就读到站点品牌色。禁止把原型 CSS 里的 `var(--x)` 换字面量。
  4. **勘误**：`09 §7.4` 的 `--bg` 更正为 `#FFFFFF`（`#F5F8FC` 是 `--bg-2` 次级底色）；补齐原型派生变量 `--deep-3/--teal-lt/--line-2/--bg-2/--card/--warn/--shadow` 的归属口径。
  5. **验收出口**：`09 §12.5` 新增「设计稿视觉比对（强制步骤）」——逐页模板抽检、同屏截图比对，扫描脚本不得替代。
- **后果**：
  - ✅ 视觉一致由「人眼翻译」变成「机器搬运」，偏差来源被消除；设计稿改样式只需替换文件
  - ✅ 原型 CSS 的响应式断点（1000/900/640/1140/1100）自动生效，无需在 SCSS 里重写
  - ✅ 令牌仍由站点配置驱动（品牌色可换），与 ADR-024 的块代码化不冲突
  - ⚠️ 原型 CSS 是全局样式，选择器较泛（如 `.hero` / `.list` / `.item`）——块内新增自定义类时必须加前缀避免撞车；站点规模增大后可能需要收敛（本期不做）
  - ⚠️ 引入 `public/` 会变更 `appHash` → 每次改样式都要重跑 `nuxt build`（可接受，样式改动本就该重建）
  - ⚠️ 原型 CSS 里的 `.proto-bar` / `.spec` / `.frame` 等**设计稿自用**样式（演示用页框）会一并进入站点产物，体积略增，但不影响页面外观（页面不用这些类）
- **否决**：把原型 CSS 转写成令牌化 SCSS 再逐块重写（就是本次要修的缺陷，翻译必然失真且双向维护）；把原型 CSS 内联进每个块组件（重复体积爆炸、断点难统一）；把原型类名改成语义化 CSS Module（与「直接复用原型」的目标矛盾，且 942 行设计稿对照表的类名映射要全部重做）。

## ADR-037 设计稿图片资产双轨（静态站点直出 + 素材库）

- **日期**：2026-10-08 · **状态**：accepted
- **上下文**：设计稿 `design/xara-bdf-site/assets/img/` 有 60 个图片文件（`cert` 18 / `device` 20 / `doctor` 4 / `env` 18）。首次建站只在数据里写了相对路径 `device/wood-lamp.jpg`，**既没把文件复制进产物，也没进素材库**，页面 `<img>` 全部 404，`doctor-card.avatar` 甚至传空串。设计稿的 `build_site_json.py` 定义了 `IMG = "/assets/img/"` 却从未用于拼 URL。
- **决策**：**双轨**，两轨内容必须可对账。
  1. **轨 1 · 静态站点直出**：整体复制到 `apps/geo/public/assets/img/**`，依赖 Vite `public/` 直出 → 构建后落进 `sites/<slug>/assets/img/**`。块内 `src` 写**站点根相对路径** `/assets/img/<group>/<file>`。
  2. **轨 2 · CMS 素材库**：同一批文件经 `POST /files/upload`（`05 §4.2`：字段名 `file`、`multipart/form-data`、服务端生成 `uploads/yyyy/mm/{uuid}.{ext}`）入 `StaticFile`，并写入 `caption/location/takenAt/imageNo`（`09 §3.5`），供后台在内容编辑器检索复用与 `gallery/env-grid/cert-grid` 的合规字段取用。
  3. **路径口径**：页面渲染一律走轨 1 的站点根相对路径（构建产物零依赖 CMS、可整包托管）；轨 2 的 `publicUrl` 用于**后台编辑态**回显与内容检索。绝对 URL 需要时统一由 shared 的 `buildSiteUrl` 拼装，**禁止硬编码域名**。
  4. **一致性校验**：产物内 `<img src>` 必须逐一可 200（新增检查项，`09 §12.4`），且 `apps/geo/public/assets/img/**` 的文件集合 = 素材库中归属本站的图片集合。
- **后果**：
  - ✅ 构建产物自包含：下载整包解压即可托管，图片不依赖 CMS 在线
  - ✅ 素材库可检索：运营在编辑器里能按 `caption/location/takenAt` 找到并复用设计稿图片
  - ⚠️ 同一份图片存两处（仓库 + 数据库），更新图片需两轨同步——本期靠脚本一次性对齐，未做自动联动
  - ⚠️ `public/` 直出的图片**未经处理**（无压缩 / 无 WebP / 无响应式），设计稿原图直接上线；图片优化列入 Backlog
- **否决**：只走素材库（产物不自包含，下载包托管后图片全丢；且 SSG 期对 CMS 有强依赖）；只走静态直出（运营在编辑器里看不到也换不了图，违背内容编辑器定位）；把图片 base64 内联进块（产物体积爆炸、无法缓存）；在构建脚本里做图片拷贝（`public/` 已由 Vite 原生处理，多一层反而要维护构建脚本）。

## ADR-038 页面级节奏提示（section hint）与 telbar 逐页补全

- **日期**：2026-10-08 · **状态**：accepted
- **上下文**：原型（`design/xara-bdf-site/*.html`）的间距节奏是**页面级**排版——`section{padding:56px 0}`，深浅底 `.alt` 交替由整页视觉决定，单个块自身不携带该信息；块代码化（ADR-024/036）后每块独立渲染，`BlockRenderer` 只能按块 key 猜底色，导致「每个 itemcard 各占一个 56px 节」「alt 交替错位」等节奏偏差（§12.5 首轮比对的主要差异来源）。同时原型 16 页中 15 页尾部有 `.telbar` 预约条（尾句逐页不同），首轮建站只有首页带了，其余页面尾部 CTA 整体缺失。
- **决策**：
  1. **section hint**：块实例支持可选 `section` 字段（`plain` / `alt` / `plain-flush` / `alt-flush` / `head` / `none`），由建站数据源按原型逐页标注；未设置时回退 `BlockRenderer` 内置 `SECTION_OF` 清单。提示仅决定外层 `<section class="site-section">` 的底色与内边距，不进块数据表单（`normalizeBlockInstances` 透传、计入 `computePageContentHash`，改动即触发待发布）。
  2. **head 合并**：`section-head` 与紧随其后的内容块合并为一个 `<section>`（原型 sec-head + grid 同节）；`hero-panel` 紧随 `hero-dark` 时合并进 hero 的 `panel` 字段——两条合并规则让「节」的粒度与原型一致，而非块粒度。
  3. **telbar 逐页补全**：建站数据源（`build_site_json.py`）内置 `TELBAR_TIPS` 映射（逐页文案提取自原型，禁止凭记忆改写），除 `about`/`entity`/法务/框架页外每页追加 `telbar` 块。
- **后果**：
  - ✅ 页面节奏与原型逐节一致（§12.5 复验通过：services 三组卡 / devices 行列 / terms 深浅交替）
  - ✅ telbar 尾部 CTA 全站补齐（158/164 页），文案与原型逐页一致
  - ⚠️ 数据源标注 `section` 是人工工序，漏标时回退 `SECTION_OF`（覆盖常用块），冷门组合仍可能错拍——靠 §12.5 抽检兜底
  - ⚠️ hint 计入内容指纹：改 hint 即「待发布」，与内容改动同等待遇（预期行为）
- **否决**：把节奏写进块组件的 scoped 样式（块粒度永远拼不出页面级交替；且违反 ADR-036「不改原型布局」）；在 BlockRenderer 里按「上一块是否 alt」自动交替（原型并非严格交替，规则化猜拍必然引入新偏差）；给 `section` 做成后台表单字段（本期建站由数据源驱动，后台暴露易误操作）。

## ADR-039 新闻/问答以独立数据表为管理源（页面降级为发布产物）

- **日期**：2026-10-15 · **状态**：accepted（取代 2026-10-14 第 42 轮「复用 Page 体系」的临时取舍）
- **上下文**：新闻资讯 / 高频问答后台管理（第 42 轮）最初把内容直接落在「Page + 块数据」形态：列表读 `Page` 树、编辑按 `pageId` 寻址、详情接口要求 `?siteId=` 参与权限校验。实测暴露三类问题：① **编辑寻址不可靠**——前端只持 `pageId`，页面被站点级操作重建后 id 漂移；且旧详情接口要求 `siteId` 而前端未传，`NaN` 比较恒 404；② **列表查询低效**——分页 / 关键词 / 分类筛选要在 `Page + Block` 的 JSON 数据上过滤，无法走索引；③ **数据与产物耦合**——管理数据与发布产物同表混存，内容字段与发布态字段互相牵连。
- **决策**：
  1. 新增独立数据表 `NewsArticle` / `FaqItem`（见 [`04`](./04-data-model.md) §8）作为**唯一管理源**：CRUD 直读直写表，列表 / 详情 / 编辑 / 删除按表记录 `id` 寻址；**详情接口不再收 `siteId` 参数**（按记录自身 `siteId` 归属鉴权，记录不存在 404、越权 403）；
  2. `Page`（`kind=detail` 详情页）**降级为发布产物**：表记录持 `pageId` 弱引用，页面缺失时保存自动补建；`slug` 创建后不可改（产物地址稳定，与 ADR-025 同口径）；
  3. 增删改后仍走既有链路：`news-faq-sync.service.ts` 事务重算派生块（`/news`、`/faq` 列表页、related-faq）→ `PublishService.enqueue` 页面级发布，保存即 `published`（见 [`06`](./06-publish-and-geo.md) §8）；
  4. 新闻 `publishDate` 必填、`YYYY-MM-DD`、**不允许早于今天**（服务端中国时区 `todayInChina()` 强校验 + 管理端弹窗禁选过去日期）；问答无发布日期字段。
- **后果**：
  - ✅ 编辑寻址可靠：`id` 是表主键，不受页面重建 / 产物操作影响；「未传 siteId 恒 404」缺陷随契约根除
  - ✅ 列表查询高效：分页 / keyword / category 落在表字段（可加索引），不再解析 JSON 块数据
  - ✅ 数据与产物解耦：管理源在表、展示形态在 Page，双方各自演进互不牵连
  - ⚠️ 需一次性迁移：`backfill-news-faq-tables.mjs` 从存量 Page 回填（本轮 7 新闻 / 102 问答，幂等可重跑）
- **否决**：继续用 Page 体系当管理源（上述三类问题无解）；页面缺失时让保存失败（运营会被产物状态卡住，弱引用 + 自动补建体验更好）；详情契约保留 `siteId` 入参（表记录自带归属，多余参数正是 404 根因）。

## ADR-040 服务前缀统一（服务端 /geoserver · 后台 /geocms/ · 绝对 apiBase）

- **日期**：2026-10-15 · **状态**：accepted（不推翻 ADR-016 / ADR-021：配置集中与局域网自适应规则继续有效，本条裁决**全局前缀与基址形态**）
- **上下文**：三端长期裸奔在根路径下（服务端 `/api`、后台 `/`）：① `/api` 是 NestJS 文档默认前缀，无辨识度，反向代理难以按路径做分流 / 缓存 / 限流等差异化策略；② `apiBase` 一旦是相对前缀，**服务端消费者**（`build-sites.mjs` / `sync-blocks.mjs` 构建脚本、GEO nitro `/static` 代理、预览票据）没有「页面同源」可改写，相对地址直接失效——这些进程不在浏览器里。
- **决策**：
  1. **服务端全局前缀 `/api` → `/geoserver`**：`main.ts` `setGlobalPrefix`、Swagger `/geoserver/docs`、容器 healthcheck 同步；
  2. **管理后台挂 `/geocms/` 基础路径**（`nuxt.config.ts` `app.baseURL`）：后台内 401 判断等「当前路由」口径统一走 `config/api/http.ts` 的 `currentRoutePath()` 剥离 baseURL；新标签页地址统一 `window.open(router.resolve(path).href, ...)`（`window.open` 直写相对路径不带前缀，打开即 404）；
  3. **`apiBase` 必须为绝对基址**：`config/index.mjs` 缺省派生 `http://<PUBLIC_HOST>:<PORT_SERVER>/geoserver`（显式 `API_BASE` 优先、去尾斜杠）；浏览器端仍保留 ADR-021 的局域网自适应（回环基址换页面主机名）。
- **后果**：
  - ✅ 前缀可辨识：nginx / 网关按路径分流、限流、封禁有明确锚点，针对 `/api` 的通用扫描探测不再命中
  - ✅ 服务端消费者零特判：绝对 URL 所见即所得，构建脚本与代理不做同源改写；显式 `API_BASE` 不以 `/geoserver` 结尾时视为已指向服务根
  - ⚠️ 前缀是全局约定：新增对外入口（webhook / 开放接口）必须落在 `/geoserver` 下；后台站内跳转禁止 `window.open` 裸写相对路径（见 [`03`](./03-frontend-architecture.md) §2.2 规则 15）
- **否决**：相对前缀 `apiBase`（服务端消费者无法解析）；维持 `/api`（默认值无辨识度、代理规则易冲突）；后台维持根路径（SPA 资源与站点 / 服务端路径同域时互相遮蔽）。

## ADR-041 Linux 直装上线采用 PM2 守护（生成式 PM2 配置 + release --build-only）

- **日期**：2026-10-16 · **状态**：accepted（局部修订 ADR-034 的否决项——仅「进程管理器」一条；两条命令分离、体检阻断制、端口清理等其余结论全部继续有效）
- **上下文**：平台首次公网上线，形态定为单台 Linux 服务器直装（不使用 Docker）。既有链路里 `pnpm release:*` 在**前台托管**三端进程，SSH 会话断开即全部退出，公网生产不可接受。ADR-034 曾把长期常驻指向 systemd / Docker，但实际取舍中：systemd 需为三端各写一份 unit，环境变量要么散落 unit 文件（与 `config/index.mjs` 派生体系脱节、形成第二份事实来源），要么改造派生逻辑，维护成本高且易漂移；Docker 本期不采用。需要的是崩溃自动拉起、开机自启、日志留存、平滑 reload，且**不复制**端口 / 连接串 / 密钥的派生口径。完整操作口径沉淀在新增的 [`10-launch-runbook.md`](./10-launch-runbook.md)。
- **决策**：
  1. **进程守护选 PM2**：服务器上全局安装（`npm i -g pm2`），**不进 `package.json`**——它是服务器运行时工具而非工程依赖，不破坏「根脚本零第三方依赖」约定；由 `pm2 startup systemd` 桥接开机自启；
  2. **PM2 配置采用「生成式」**：新增 `scripts/pm2-config.mjs`（零第三方依赖），以 `loadConfig()` + `buildAppEnv()` 派生三端进程定义（`name` / `cwd` 对齐各应用包目录 / `script` 与 `start:prod` 同口径 / `env` 为派生变量），写仓库根 `ecosystem.config.json`（PM2 原生 JSON 格式）；生成文件含 `DATABASE_URL` / `JWT_SECRET` 等密钥 → **gitignore 不入库**，env 变更后重新生成；
  3. **上线器增加 `--build-only`**：体检（含数据库只读检查）→ 构建后即停止，不释放端口、不启动进程；服务器上的进程启停一律交给 PM2（`pm2 start` / `pm2 startOrReload --update-env`）；
  4. **命令族不变**：`db:deploy*`（结构）→ `release --build-only`（体检 + 构建）→ `pm2 startOrReload`（守护重启）——只是「启动」一段的执行者从上线器前台换成 PM2，两条命令分离的边界与审计点不受影响。
- **后果**：
  - ✅ 进程常驻与开机自启不再依赖 SSH 会话；崩溃自动拉起（`min_uptime` / `max_restarts` 约束防风暴重启）
  - ✅ 端口 / 连接串 / API 基址 / 密钥仍只有 `env/` + `config/` 一个事实来源，PM2 配置是派生产物
  - ✅ 上线器的体检与构建链路（JWT 占位值检查、迁移落后拦截、串行构建）在服务器上继续生效
  - ⚠️ `ecosystem.config.json` 含密钥、每台服务器各自生成，**禁止提交或跨机拷贝**
  - ⚠️ `--update-env` 漏带会让 PM2 沿用旧环境变量跑新代码（必要时 `pm2 delete` 后重新 start）
  - ⚠️ ADR-034 否决 PM2 的理由（新增依赖与运行形态）被本次决策推翻，属形态升级而非方案回退
- **否决**：systemd unit 直写（三份 unit 手工同步派生变量，env 变更易漂移，且缺 reload / 日志命令面）；手写 `ecosystem.config.js`（CJS 进程无法同步 require ESM 派生逻辑，手写即第二份事实来源）；Docker 形态（本期不用，形态保留于 [`07`](./07-deployment.md)）；PM2 cluster 多实例（三端单机单实例即可，无多实例需求；构建缓存与产物目录共享也不支撑）。

## ADR-042 自包含部署包：`pnpm pack:deploy` 产出 `deploy/`，服务器侧 `node start.mjs` 一条命令运行

- **日期**：2026-10-16 · **状态**：accepted（ADR-041 的 PM2 路径继续有效，部署包是与之并列的**免源码上线形态**；两条命令分离原则不变——部署包内 `node db.mjs` 与 `node start.mjs` 仍是结构与代码两条独立命令）
- **上下文**：源码链路（§3~§5：git pull → pnpm install → db:deploy → release --build-only → PM2）要求服务器具备 git / pnpm / Node 全套工具链，且 install、构建在低配服务器上耗时与内存压力都不小。实际诉求是：**本地构建好产物后，产出一个可整体拷贝的自包含文件夹，服务器上只要有 Node + MySQL + nginx，解压后一条 `node start.mjs` 即可运行**，并要求同一条命令能同时管理多个应用进程（本仓库为三端）。
- **决策**：
  1. **打包器 `scripts/pack-deploy.mjs`**（本地执行，零第三方依赖）：体检三端产物齐备后，把 `config/`（派生逻辑）、`env/.env.<环境>`（含密钥）、运行时模板（`scripts/deploy-runtime/`）与应用产物汇集到仓库根 `deploy/`（gitignore）；
  2. **依赖收集用 `pnpm deploy --node-linker=hoisted`**：对 `@trillion/server`（dist + prisma 迁移 + uploads + 全量依赖，含 prisma CLI 与 tsx）与 `@trillion/geo`（源码 + nuxt 工具链 + `.output` + `sites/` 产物 + `.*.build` 构建缓存）产出**零 symlink** 的自包含目录（v12.2.0 起 workspace 依赖自动重写 `file:`）；admin 只拷 `.output`（Nitro 自包含产物）。**geo 必须带构建环境**：服务端发布任务 spawn `node apps/geo/scripts/build-sites.mjs`（内容发布 → 自动 SSG 的闭环），部署包内没有它则后台发布静默失败；
  3. **运行时入口 `start.mjs`（清单驱动）**：进程清单来自部署包内 `config/apps.mjs`（当前三端），每端 spawn `node <script>`（cwd 对齐各应用包目录，env 由 `buildAppEnv()` 派生——端口 / 连接串 / API 基址 / 密钥仍只有 `env/` + `config/` 一个事实来源）；崩溃自动重启（4s 间隔、上限 10 次）、`start`（前台）/ `daemon`（后台 detached + 日志落盘 + pid 文件）/ `stop` / `status` / `restart` 子命令；
  4. **数据库入口 `db.mjs`**：`status` / `deploy`（prisma migrate deploy）/ `seed`——直接调用部署包内 server 自带的 prisma CLI 与 tsx，服务器无需 pnpm；**结构与代码仍是两条命令**（先 `node db.mjs deploy` 再更新代码重载）；
  5. **包体不做瘦身**：server 全量依赖约 430MB（含构建期 devDeps）换 migrate / seed / SSG 构建开箱可用，压缩后约 250~300MB——正确性与「免装工具链」优先于体积。
- **后果**：
  - ✅ 服务器最小依赖：Node 20+（含 npm，装 MySQL / nginx 时已有）、MySQL、nginx；**无 git / pnpm / PM2 要求**，SSH 断开不影响 daemon
  - ✅ 发布闭环不受损：后台改内容 → 服务端 spawn 部署包内 `apps/geo/scripts/build-sites.mjs` 增量构建 → `sites/<slug>/` 更新
  - ✅ 派生体系零复制：部署包内 `config/` 是同一套文件的拷贝，`start.mjs` / `db.mjs` / nginx 模板全部消费它
  - ⚠️ 部署包含密钥与全量产物 → **gitignore，禁止入库**；更新代码 = 本地重新打包整体覆盖（`.run/`、`logs/`、`uploads/` 会被覆盖——uploads 首次部署后服务器侧新增文件需在覆盖前备份或改用增量替换）
  - ⚠️ 包体约 800MB（压缩 250~300MB）；`--node-linker=hoisted` 放弃 .pnpm 去重，属可接受代价
  - ⚠️ 部署包内不含端口释放器：启动前确保 3000~3002 未被占用（`node start.mjs status` 可探测）
- **否决**：直接拷贝 workspace `node_modules`（pnpm 目录树由 symlink/junction 组成，Windows→Linux 拷贝必断链）；`pnpm deploy` 默认 isolated linker（同样含 symlink，跨文件系统拷贝易断）；`--prod` 瘦身（prisma CLI / tsx 属 devDeps，剔除后 migrate / seed 失效，手挑工具链包清单脆弱）；把守护逻辑外包给 systemd unit（回到 ADR-041 已否决的口径漂移问题）；服务器上二次 `pnpm install`（违背「免工具链」初衷且 hoisted 目录二次安装行为不可控）。

## ADR-043 主键统一改为应用生成的字符串 ID（uuid v7），全库禁用自增

- **日期**：2026-10-20 · **状态**：accepted（取代全部 `Int @id @default(autoincrement())` 约定；ADR-005/011/039/040 等依赖 id 形状的条目一并按本条调整）
- **上下文**：线上库 22 张表**一个主键都没有** —— id 列在，但既无 PRIMARY KEY 索引也无自增。Prisma 对 `@id @default(autoincrement())` 的写入会**省略 id 列**，库端既无默认值也无自增，于是 INSERT 一律被 MySQL 拒绝（`Null constraint violation on the fields: (id)`；给自增列补自增时报 1075 `Table ... doesn't have a primary key`），整站重建、新闻/问答保存等**所有新建操作全部失败**。本地库同一套自增 id 设计却完全正常 —— 根因是「缺主键」，**自增本身不是病因**。
  团队借此决定：不再依赖数据库侧自增，**ID 一律由应用生成**，把「ID 归应用掌握」固化为架构约定。
- **决策**：
  1. 主键形态统一为 `id String @id @db.VarChar(36) @default(uuid(7))`：uuid v7 由 Prisma Client **在应用侧生成**，且按时间有序，保留 InnoDB 聚簇索引的插入局部性。
  2. 指向其它表的所有标量列（`siteId` / `channelId` / `parentId` / `roleId` / `menuId` / `*FileId` 等）同步改为 `String @db.VarChar(36)`，**禁止 Int 外键**；共 20 个 model 一起改（清单见 [`04-data-model.md`](./04-data-model.md) §2.1）。
  3. `RoleMenu` 保留 `@@id([roleId, menuId])` 复合主键：本条禁的是**自增**，不是复合主键；`roleId` / `menuId` 本身仍随各自主键改为字符串。
  4. **字符串 ID 不替代主键约束**：每张表仍必须有真实 PRIMARY KEY；线上 22 张表缺键是独立缺陷，按 [`04-data-model.md`](./04-data-model.md) §6 修复，二者不可互相顶替。
  5. 接口边界：`:id` 路径参数统一改用 `ParseUUIDPipe`（uuid v7 是标准 UUID 形态），服务端删除全部 `Number(id)` 转换。
  6. **数据迁移采用「重映射」而非重建**：存量内容一条不丢。由 `apps/server/prisma/` 下一次性 tsx 脚本完成——读旧库 → 每行分配 uuid v7 → 建立 `old → new` 映射 → 改写外键列**及内嵌 JSON 内的 id**（`Page.blocks`、`Page.draft`、`PublishTask.targets`、`Menu` 父子关系等，SQL 无法可靠处理）→ 写入新结构库。
  7. 规范落地：`AGENTS.md` §5、[`04-data-model.md`](./04-data-model.md) §2.1 同步写入硬规则；后续如需例外（含自增列）必须先新增 ADR。
  8. **迁移历史同步重建**：旧迁移链（`20261005103528_init` / `*_add_menu` / `*_rbac_user_role_menu` / `*_add_site_domain` / `*_add_news_faq_tables` 等）与当前 schema 已严重漂移（缺 `path` / `content_hash` / `draft` / RBAC 外键等），2026-10-20 以 `prisma migrate diff --from-empty` 生成的**单条基线** `20261020120000_init_id_string` 整体替换（21 张表全量 DDL + 全部外键 + 真实主键），旧迁移目录删除；空库 `db:deploy*` 即建成当前结构（见 [`04-data-model.md`](./04-data-model.md) §6）。实现上重映射走 SQL（跨库 `INSERT ... SELECT` + `old→new` 映射表改写全部外键列），仅内嵌 JSON 的 id 用脚本回填——比逐行 ORM 写入更快且不依赖 Prisma 类型。
- **后果**：
  - ✅ ID 完全由应用掌握，不再依赖数据库侧自增配置；跨环境 / 多库合并天然无冲突
  - ✅ uuid v7 有序，聚簇索引插入局部性接近自增，避免随机 UUID 的页分裂与写放大
  - ✅ ID 不可枚举（后台本有鉴权，此为纵深防御）
  - 📌 旧库全量导出留存 `apps/server/_backup-db-20261020/`（不入库），本地库已按新结构整体重建并逐表校验行数与引用完整性
  - ⚠️ 键宽 36 字节（int 为 4 字节）：高频事件表（`TrackEvent` / `AiCrawlEvent`）行体积与索引明显增大，是本次改造的主要代价
  - ⚠️ 破坏性跨端变更：`packages/shared` 里 `id: number` → `string`，admin / geo 两端所有把 id 当数字用的位置（`Number(id)`、`--pages` 过滤、脚本 `SITE_ID`）必须同步；新旧版本不兼容（同仓发布，无外部消费者）
  - ⚠️ 迁移必须脚本化 + 校验：漏改内嵌 JSON 里的 id 会留下**静默坏数据**（块指向不存在的资源），SQL 层面看不出来
  - ⚠️ 单向改造：回退到自增需反向重映射，成本更高
- **否决**：只补齐主键、继续用 Int 自增（改动最小、可最快解封线上，但未满足「统一 ID 形态」诉求，且仍依赖数据库侧配置）；`cuid()/cuid2()`（非单调，索引局部性差，且无跨语言标准）；`uuid()` v4（随机键导致聚簇索引页分裂）；`ULID`（Prisma 无内建默认，需自写生成器）；数据库侧 `AUTO_INCREMENT` / `DEFAULT(UUID())`（违背「ID 由应用生成」）。
